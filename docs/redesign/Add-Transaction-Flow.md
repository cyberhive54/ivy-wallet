# Add Transaction Flow — Redesign Spec

Status: Phase 1 (data layer) implemented. Phase 2 (UI) in progress.
Branch: `cyberhive54/update`

## Goal

Redesign the Add/Edit transaction flow (Income / Expense / Transfer) and the
surrounding category/tag/account surfaces so they fit the fork's theme system
(Look × Mode × Accent), following Apple/Cupertino design language
(see `docs/redesign/../assets` and the apple-design conventions: springs,
interruptibility, translucency for hierarchy, size-specific typography,
reduced-motion fallback, 48dp targets, system Back always works).

## Decided decisions (user-approved)

1. **Layout**: Amount-first full-sheet redesign of `EditTransactionScreen`;
   keep "form top + docked sheet bottom" replaced by hero amount.
2. **Type switching**: keep the top-right type pill
   (`ChangeTransactionTypeModal`) for Income/Expense (not Transfer/Loan).
   Keep the calculator nested in the amount step.
3. **Transfer**: `From` / `To` account rows visible from the start
   (above/below the amount hero), same-account validation inline.
4. **Necessity field** (expenses only, optional): `UNKNOWN / MUST / NEED / WANT`.
   Stored on `TransactionEntity.necessity` (nullable TEXT, schema v131).
   JSON backup carries it automatically (entity @Serializable).
   CSV export appends a `Necessity` column (after ID); CSV import maps it as an
   optional field (`MapNecessity` / `parseNecessity`), expenses only.
5. **Category ↔ transaction-type mapping**: categories belong to any
   combination of Income/Expense/Transfer (default = ALL, legacy behavior).
   Stored on `CategoryEntity.transactionTypes` (comma-separated names, null = ALL),
   schema v131 migration (`Migration130to131_NecessityAndCategoryTypes`).
   Carried by JSON backup automatically; editable in the category create/edit UI.
6. **Categories page**: top full-width filter bar (ALL / EXPENSES / INCOME / TRANSFER —
   clears the cluster), second row = search + add button side by side;
   searching an unknown category shows "No such category" and an
   "Add {searched name}" row that pre-fills the create flow. Reorder/"sort by"
   page redesigned to the theme system. Categories & Tags pages get the dock.
7. **Tags**: searchable modal stays; Tags page follows the categories design.
8. **Dock**: root-level *contextual* dock (not just the 4 tabs). On pushed pages
   (Categories/Tags) the dock stays visible and its `+` becomes
   Add Category / Add Tag; tabs keep Add Transaction/Add Planned.
9. **Accounts flow**: list is fine; details stay dual-purpose
   (`TransactionsScreen(accountId=…)`) for now — restyle, do not split.
10. **Minimal functional changes** elsewhere; behavior preserved unless listed above.
11. **Order of work**: transaction flow first, accounts second.

## Data model changes (Phase 1 — done)

- `TransactionEntity.necessity: String?` (nullable, default null)
- `CategoryEntity.transactionTypes: String?` (nullable, default null = ALL)
- Migration `Migration130to131_NecessityAndCategoryTypes` (130 → 131)
- `Necessity` enum (`com.ivy.base.model`)
- Domain: `Expense.necessity: Necessity? = null`, `Category.transactionTypes: Set<TransactionType> = ALL`
- Mappers: `TransactionMapper` (Expense only), `CategoryMapper` (null = ALL)
- Backup: JSON backup carries both automatically
- CSV: `IvyCsvRow.Columns` gains trailing `"Necessity"`; export writes it
  (expenses only); import maps it via optional field `Necessity`
  (`CSVEvent.MapNecessity`, `ParseFields.parseNecessity`, `CSVImporterV2`)

## Open items / risks

- `schemas/.../131.json` is generated by the next Room build (cannot be
  produced without compiling). Do not hand-write it.
- `Migration130to131` not yet covered by a migration test
  (mirror `Migration128to129Test.kt`).
- No reduced-motion fallback yet anywhere in the new UI.
- GLASS look below API 31: translucency without blur — needs opacity raise.
- Backup of fork-only SharedPrefs (`SETTINGS_LOOK`, `SETTINGS_ACCENT_COLOR`,
  `SETTINGS_DOCK_TRANSLUCENT`) is NOT covered by Room backup — look/accent
  reset on restore. Needs a decision: extend `getSharedPrefsData()` or accept.

## Implementation plan

Phase 1 — data layer (done, this commit): entities, migration v131, mappers,
JSON backup (automatic), CSV round-trip wiring.

Phase 2 — add-transaction amount-first full sheet (done): `EditTransactionScreen`
redesign; hero amount (+calculator keypad kept), From/To rows visible from
the start, top-right type pill (`TypePill`), `BottomActionBar` (accent CTA:
Add/Save/Pay/Get), whole flow restyled to Look/Mode/Accent tokens
(`ivyInter`, hairlines, accent primary, `CircleButtonFilled` top bar).

Phase 3 — modals (done, minimal functional changes): `IvyModal` frost
upgrade (pure panel + hairline border) restyles every modal for free;
`ChooseCategoryModal` rebuilt on `CupertinoCategoryPicker`;
`CategoryModal` gained transaction-types multi-select;
`AmountModal`/`AccountModal` keep legacy logic with frosted chrome.

Phase 4 — categories & tags pages (done): `CupertinoCategoryPicker` rebuilt
page (type chips All/Expenses/Income/Transfers, search+add row,
"No such category" + "Add {name}" create-named-category flow incl. prefilled
`CategoryModalData.initialName`); categories page in new
header/categoryCard layout — `CategoriesBottomBar` removed → dock contextual
"+"; tags page redesigned (big Inter title, back button, no add button).
Sort-by modal rows re-styled to accent selection; reorder
modal (`ReorderModalSingleType`) Inter title + accent confirm button.

Phase 5 — root contextual dock (done): `MainBottomBar(BottomBar)` gained
`overrideAddAction` — pushed screens (Categories/Tags) render the floating
dock in `IvyNavGraph` and the "+" emits `ContextualDock.requestAdd()`,
collected in each page's `LaunchedEffect` to open its add modal.
MainScreen tabs keep the radial wedge menu unchanged; tab taps from pushed
pages jump back to `MainScreen` with that tab selected.

Phase 6 — accounts (done, surgical): Inter big titles on Accounts tab,
Inter reorder rows (accounts + categories share `ReorderModalSingleType`),
account details typography pass. Accounts list keeps its cards, balance math
and reorder flow unchanged (functional parity).

Deliberately skipped: dedicated `AccountDetails` split (still dual-purpose
`TransactionsScreen(accountId=…)` restyled in place per earlier decision),
last-account delete guard, transfers-to-deleted-account cleanup,
"Adjust balance" transparency — all logged here; ask for them if you want
them fixed.

Known risk: nothing has been built yet. First build must regenerate
`schemas/.../131.json`. Migration test for 130→131 not yet written
(mirror `Migration128to129Test.kt`).
